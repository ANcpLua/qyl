qyl — component taxonomy · 1.0.0 target

Three orthogonal axes · two planes · canonical 1.0.0 names — theory until the rename lands (§2 maps target ↔ today)

This page is a view, not a source. The normative document is ARCHITECTURE-1.0.0.md in the repo root — on any conflict, the Markdown wins. A second source of architectural truth would be exactly the duplicate-contract failure the architecture itself forbids.
qyl is one schema-owned modular platform: one dependency graph, one verification pipeline, and multiple independently shipped artifacts. MCP, CLI, instrumentation, conventions, collector, Workbench, and Runner each keep one clear responsibility without owning duplicate contracts. The matrix keeps protocol role, logical responsibility, and deployment packaging as separate axes, because flattening them buried the load-bearing fact: only 2 of 9 components are on the MCP plane at all — everything else is a conventional telemetry pipeline (instrument → export → collect → API → UI) speaking OTLP/HTTP/CLI, and the whole closed/open asymmetry lives on one axis, at two nodes. One graph, one truth, many artifacts.

    3 Industry precedent — each validates one boundary

    4 Pro / contra

    Single “Role” column

    Pro
    • Minimal, one-glance; fine as a README intro.
    • Low maintenance.
    Contra
    • Fuses three axes → ambiguous cells.
    • Can’t express a multi-role component (the collector is OTLP receiver and HTTP API).
    • Hides the plane split, the 3-dashboard overlap, the missing collector-ingest + instrumentation.
    • Buries the load-bearing fact: only 2 components are MCP.

    3-axis matrix

    Pro
    • Orthogonal → unambiguous cells; multi-role representable.
    • Surfaces the plane cut, redundancy, and gaps.
    • Pins the closed/open asymmetry to one axis + two nodes.
    • Each axis answers a real question (packaging → “can it run in a browser?”; protocol → closed vs open type discipline).
    Contra
    • Heavier to keep current.
    • Tempts over-decomposition of genuinely atomic components.
    • Less scannable for a newcomer than a one-liner.

    5 Recommendation

    Keep a one-line-per-component table as the README front door — using exactly these canonical names — and back it with this 3-axis matrix for architecture decisions, with the MCP-plane / product-plane split as the top-level cut. The boundary law: Qyl.Telemetry.Hosting composes the producer pipeline and ends at the OTLP exporter; Qyl.Collector.* begins where the exporter ends; Qyl.Cli and qyl.mcp/server are clients and projections of the collector API, never second owners of its contract; the only shared artifact across planes is the generated vocabulary. One graph, one truth, many artifacts.
